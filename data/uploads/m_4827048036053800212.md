## Abstract / 摘要

Long contexts improve the usefulness of large language model services but increase the time before generation can begin. Reusing a context's key–value (KV) cache avoids repeated prefill computation, yet loading that cache from another machine can introduce substantial network delay. CacheGen addresses this problem through a codec tailored to KV tensors and a streaming policy that adapts representation choices to available bandwidth and a latency objective. The authors report 3.5–4.3× smaller KV representations at similar task quality. At 3 Gbps, CacheGen delivers a 3.2–3.7× TTFT speedup over the default quantization baseline. We examine how its codec and streaming policy produce these gains. Drawing on RobustMPC [3] and DynamicKV [4], we then propose prediction-error-aware KV streaming and task-aware precision selection. Together, these extensions connect network-aware delivery with task-specific quality requirements. [1, §§1, 5–9]

长上下文能帮助大语言模型完成复杂任务，但也增加了开始生成前的等待时间。复用上下文的 KV Cache 可以避免重复执行 prefill；不过，当缓存位于其他机器时，加载缓存本身又可能成为网络瓶颈。CacheGen 通过针对 KV 张量设计的编码器，以及根据带宽和延迟目标调整传输方式的策略，解决这一问题。在相近任务质量下，论文报告 KV 表示缩小 3.5–4.3 倍；在 3 Gbps 下，相比默认量化基线，TTFT 加速 3.2–3.7 倍。本报告解释编码器与传输策略如何产生这些收益，并借鉴 RobustMPC [3] 和 DynamicKV [4]，提出考虑预测误差的 KV 传输决策、按任务选择编码精度两个方向，将网络感知传输与任务质量需求结合起来。

## 1. Introduction and research problem / 背景与研究问题

### 1.1 Why context reuse matters / 为什么要复用上下文

An LLM request may include a long context followed by a shorter user question. Examples include a report used for several financial questions or a conversation history reused in later turns. During prefill, the model processes the context and produces intermediate K and V tensors. Saving those tensors allows subsequent requests with a compatible reused context to avoid repeating that computation. CacheGen focuses on accelerating the loading of such reusable state. [1, §§2–3]

LLM 请求通常包含较长的背景材料和较短的问题，例如围绕同一份报告连续提问，或在多轮对话中重复使用历史记录。模型在 prefill 阶段处理这些输入并生成 K、V 中间张量。保存这些张量后，后续请求可以复用兼容的上下文状态，减少重复计算。CacheGen 关注的是如何更快加载这些可复用状态。

### 1.2 The hidden network bottleneck / 隐藏的网络瓶颈

GPU memory cannot necessarily retain every reusable context. Cache eviction, a remote storage service, or a request arriving at a different inference server can require cache transfer over a network. KV tensors can be much larger than the original text. Consequently, transmitting KV may take longer than recomputing it from text. The central problem is to reduce total context-loading delay while preserving useful generation quality. CacheGen addresses it through joint compression and adaptive delivery. [1, §3]

GPU 显存无法始终容纳所有可复用上下文。缓存被换出、使用独立存储服务，或请求被路由到另一台推理服务器，都可能触发跨网络传输。KV 张量的体积可能远大于原始文本，因此传 KV 未必总比传文本后重算更快。核心目标是在保持生成质量的同时降低整体加载延迟，CacheGen 通过压缩与自适应传输共同实现这一目标。

| Context-loading method / 加载方式 | Main benefit / 主要收益 | Main cost / 主要代价 |
|---|---|---|
| Transfer text and run prefill / 传文本后 prefill | Small network payload / 网络数据少 | Repeated GPU computation / GPU 重复计算 |
| Transfer quantized KV / 传量化 KV | Reuses precomputed state / 复用已有状态 | Large payload can dominate delay / 数据量可能主导延迟 |
| CacheGen / 压缩与自适应传输 | Reduces payload and selects a suitable representation / 降低数据量并选择合适表示 | Codec, storage, and decision overhead / 编解码、存储及决策开销 |

### 1.3 Connection to COMP5311 / 与课程的联系

CacheGen is an application-layer response to network constraints. It changes the representation and amount of data sent over a connection while relying on the transport layer to deliver it. Its choices connect transmission delay, measured throughput, application quality, and a service-level objective (SLO). This resembles adaptive media streaming in its use of pre-encoded versions, but an LLM consumes internal tensor state rather than video frames. Quantization controls the size–quality trade-off. [1, §§4–5]

CacheGen 从应用层应对网络约束：改变连接上传输的数据表示和大小，底层仍依赖传输协议完成交付。它将传输延迟、实际吞吐量、应用质量和服务级目标联系起来。预先编码多个版本的思路类似自适应视频流，但传输的是模型内部状态。量化调节体积与质量的权衡。

## 2. Background and analytical framework / 基础概念与分析框架

### 2.1 KV cache, prefill, and TTFT / KV Cache、prefill 与首 token 延迟

Prefill processes the input tokens. Autoregressive generation then uses the resulting cache while producing new tokens. Time to first token (TTFT) measures the interval from query arrival to the first generated token. In this paper, that interval includes context loading and processing the new question. CacheGen targets this context-loading interval before generation begins. [1, §§2.1, 7.1]

Prefill 负责处理输入；之后，自回归生成阶段利用已有 KV Cache 逐步输出新 token。TTFT 指请求到达至产生第一个 token 的时间。在本文实验中，它包含上下文加载和新问题的处理时间。CacheGen 优化的正是生成开始前的这段加载时间。

## 3. CacheGen design / 系统设计

### 3.1 End-to-end workflow / 端到端流程

Offline, CacheGen computes a context's full KV cache, splits it along the token dimension, encodes each context chunk at multiple compression levels, and stores the resulting bitstreams. Online, it retrieves chunks in order, chooses a representation for each chunk, decodes received KV or recomputes KV from text, and supplies the reconstructed state to the LLM. It pipelines transmission of chunk \(i\) with decoding of chunk \(i-1\). Preparing versions offline makes representation selection available immediately when a request arrives. [1, §§5.3–6]

离线阶段，系统先计算完整上下文的 KV Cache，再沿 token 维度划分 chunk，分别生成多个压缩等级的码流并存储。在线阶段，系统按顺序获取 chunk，为每块选择表示方式，解码收到的 KV 或从文本重算，再将恢复出的状态交给模型。第 \(i\) 块的网络传输可以与第 \(i-1\) 块的解码重叠。离线准备多个版本，使系统能在请求到达时直接选择合适的表示。

### 3.2 Codec: observations and corresponding mechanisms / 编码器：观察与机制

| Empirical observation / 实验观察 | Mechanism / 对应机制 | Interpretation / 理解 |
|---|---|---|
| Nearby tokens have correlated KV values / 相近 token 的 KV 值相关 | Anchor-based deltas / 基于锚点的差分 | Deltas have a more concentrated distribution / 差值分布更集中 |
| Earlier layers show greater loss sensitivity in the tested workloads / 测试中浅层对损失更敏感 | More conservative quantization in earlier layers / 浅层采用更保守的量化 | Allocates precision where loss is more harmful / 将精度用于更敏感的部分 |
| Layer and channel grouping reduces entropy more than grouping by token position / 按层和通道分组更能降低熵 | Separate arithmetic-coding distributions / 分别建模并算术编码 | Exploits statistical differences across groups / 利用组间统计差异 |

**Anchor-based delta encoding.** The default group contains ten consecutive tokens. CacheGen encodes the first token as an anchor and represents each remaining token relative to that same anchor. Referencing a shared anchor allows parallel processing rather than requiring a serial chain of adjacent-token reconstruction. Anchor tensors use 8-bit quantization because their errors affect the group. [1, §5.2, Figure 6]

**基于锚点的差分编码。** 默认每组包含 10 个连续 token。第一个 token 是 anchor，其他 token 都保存相对该 anchor 的差值。这避免了逐个依赖前一 token 的串行恢复方式，有利于并行处理。Anchor 使用 8-bit 量化，因为它的误差会影响整组的恢复。

![Original Figure 6: anchor-based delta encoding](assets/fig6.png)

*Source: [1], Figure 6, PDF p.6 / printed p.43. Anchor groups support parallel reconstruction. / 锚点分组支持并行恢复。*

**Layer-dependent quantization.** CacheGen partitions transformer layers into three groups and applies progressively larger quantization bins from earlier to later groups. Larger bins introduce larger rounding errors but require fewer bits after coding. This allocation follows the authors' empirical sensitivity results and concentrates precision in the layers where it most benefits response quality. [1, §§5.1–5.2]

**分层量化。** 系统将 Transformer 层分成三组，较浅层使用较小量化间隔，较深层使用较大间隔。较大间隔会增加舍入误差，但可以得到更紧凑的编码。这一分配依据作者的敏感性实验，将精度集中用于更影响回答质量的层。

**Arithmetic coding.** After quantization, CacheGen groups values by channel and layer and applies lossless arithmetic coding to the discrete symbols. CUDA acceleration reduces codec delay. Arithmetic coding itself is lossless, but the preceding quantization is lossy. The complete system therefore has a size–quality trade-off. [1, §§5.2, 6]

**算术编码。** 量化后，系统按层和通道对离散符号进行无损算术编码，并通过 CUDA 加速降低开销。算术编码是无损的，但之前的量化有损，因此整个系统仍存在体积与质量的权衡。

### 3.3 Streaming adaptation / 自适应流式传输

The default streaming chunk contains approximately 1.5K tokens. It differs from the ten-token group used inside the codec. Each chunk has independently decodable representations. CacheGen measures the preceding chunk's throughput, assumes that throughput persists for the remaining transfer, estimates completion times, and selects a low-loss feasible configuration under the remaining SLO budget. Text recomputation is also a candidate when its estimated time fits the budget. [1, §5.3 and Appendix C.1]

默认传输 chunk 约为 1.5K tokens，与编码器内部的 10-token 差分组不同。每个 chunk 的表示可以独立解码。系统根据上一块的吞吐量估计后续带宽，并结合剩余 SLO 时间选择损失较小且预计可按时完成的配置。如果预计重算也能满足时间预算，文本方式同样可以成为候选。

Per-chunk feedback lets CacheGen update its configuration within one chunk of a bandwidth change. Smaller chunks improve reaction speed but may reduce GPU batching efficiency, especially when recomputing from text. When a chunk arrives as text, the model computes its KV using the preceding chunks' reconstructed state. This preserves the context dependencies during mixed KV/text delivery. [1, §5.3]

逐块反馈使 CacheGen 能在带宽变化后至多一个 chunk 内调整配置。缩小 chunk 可以更快调整，但可能降低 GPU 批处理效率，尤其是在文本重算时。文本 chunk 的计算仍要使用此前已经恢复的 KV 状态，从而在混合传输 KV 与文本时保持上下文依赖。

## 5. Results and interpretation / 结果与解读

### 5.1 TTFT and quality / 首 token 延迟与质量

At 3 Gbps, §7.2 reports that CacheGen reduces TTFT by a factor of 3.1–4.7 relative to text recomputation and 3.2–3.7 relative to default quantization. Against the specific 8-bit baseline, the reported factor is 1.67–1.81. The separate 8-bit result specifies the gain against the higher-precision operating point. [1, §7.2, Figure 8]

在 3 Gbps 条件下，§7.2 报告相对文本重算加速 3.1–4.7 倍，相对默认量化加速 3.2–3.7 倍；若单独比较 8-bit 量化，则为 1.67–1.81 倍。单独列出的 8-bit 结果说明了相对更高精度配置的收益。

![Original Figure 8: TTFT and quality](assets/fig8.png)

*Source: [1], Figure 8, PDF p.9 / printed p.46. TTFT–quality trade-offs across models and tasks. / 不同模型与任务下的 TTFT—质量权衡。*

Figure 8 should be read as a set of trade-off curves. A point farther left has lower TTFT, but it is only preferable if its quality remains acceptable. On Accuracy and F1 panels, a useful operating point is toward the upper left. On the Perplexity panel, lower values are better, so the useful direction is toward the lower left. The curves show how CacheGen improves response time while retaining task quality.

Figure 8 展示的是多组权衡曲线：向左意味着 TTFT 更低，但仍要检查质量。Accuracy、F1 子图通常左上更好；Perplexity 子图则左下更好。这些曲线展示了 CacheGen 在保持任务质量的同时缩短响应时间的能力。

### 5.2 Cache size and complementary methods / 缓存大小与互补方法

Across the evaluated models and datasets, the paper reports 3.5–4.3× smaller KV representations than default quantization at similar task quality. Figure 9 supports this size–quality comparison. Figure 10 shows that CacheGen can further compress KV produced after H2O or LLMLingua, with reported additional reductions of 3.3–4.2× across those comparisons. The explanation is that reducing token count and encoding the remaining tensor values exploit different sources of redundancy. [1, §7.2, Figures 9–10]

在相近任务质量下，论文报告 KV 表示相对默认量化缩小 3.5–4.3 倍。Figure 9 展示体积与质量关系；Figure 10 则说明，对 H2O 或 LLMLingua 处理后的 KV，仍能进一步压缩，相关对比报告额外 3.3–4.2 倍缩减。这种互补性来自二者减少冗余的方式不同：一个减少 token，一个进一步编码剩余张量值。

### 5.3 Sensitivity to bandwidth and workload / 带宽与负载敏感性

Figure 11 examines bandwidth from 0.4–15 Gbps and 15–400 Gbps. At high bandwidth, especially above approximately 20 Gbps in the paper's discussion, absolute gains over quantization become smaller because both methods transmit quickly. Figure 12 tests concurrent requests and context length. For contexts below about 1K tokens in that experiment, CacheGen switches to loading text because it yields lower TTFT. The policy captures the benefit of compressed KV for long contexts while selecting text for shorter inputs. [1, §7.3]

Figure 11 测试 0.4–15 Gbps 和 15–400 Gbps。原文指出，高带宽下，尤其约 20 Gbps 以上，相对量化的绝对时间收益减小，因为两种方法都能快速完成传输。Figure 12 分析并发和上下文长度；该实验中，低于约 1K tokens 时系统会转向文本加载。系统在长上下文中利用压缩 KV 的收益，在较短输入中选择文本重算。

### 5.4 SLO violations under changing bandwidth / 波动带宽下的 SLO 违约

For Figure 13, the authors generate traces with per-chunk bandwidth sampled in the 0.1–10 Gbps range and average each point across twenty traces. With a one-second SLO, §7.4 reports a reduction in violation rate from 81% for quantization to 8% for CacheGen at the same quality. This 73-percentage-point reduction demonstrates the value of representation adaptation under changing bandwidth. [1, §7.4, Figure 13]

Figure 13 使用每块带宽在 0.1–10 Gbps 范围采样的轨迹，每个点平均 20 条轨迹。§7.4 报告，在相同质量、1 秒 SLO 下，量化基线违约率为 81%，CacheGen 为 8%。违约率降低 73 个百分点，体现了表示自适应在波动带宽下的价值。

### 6.2 Strengths / 贡献与优点

CacheGen makes a clear systems contribution by separating a tensor's transmission representation from its runtime representation. It uses measurable KV properties to motivate codec choices and combines compression with network adaptation. The evaluation includes optimized recomputation, several task metrics, sensitivity analysis, cost breakdowns, and ablation. Together, these experiments connect the design choices to their measured system benefits. [1, §§4–8]

CacheGen 的系统贡献在于区分“传输时的表示”和“运行时的张量表示”，并依据可测量的 KV 特性设计编码器，再结合网络自适应。实验同时包含优化后的重算基线、多种任务指标、敏感性分析、开销分解和消融，共同解释了设计选择与系统收益之间的关系。

### 6.3 Operating conditions and design priorities / 工作条件与设计重点

CacheGen's core use case is a long context reused across requests and loaded from remote storage. Compression reduces its network footprint, while precomputed KV avoids repeated prefill. Figure 12 shows that the system also selects text recomputation for short inputs, matching the delivery route to the GPU–network balance. [1, §§3, 7.3]

CacheGen 的核心场景是跨请求复用、从远程存储加载的长上下文：压缩减少网络数据量，预计算 KV 减少重复 prefill。Figure 12 同时展示了系统为短输入选择文本重算，根据 GPU 与网络的平衡匹配加载方式。

Two design priorities follow: account for prediction error when planning delivery, and align encoding precision with task-quality requirements. RobustMPC [3] supplies the uncertainty-aware planning principle, while DynamicKV [4] provides evidence for task-dependent cache allocation. These connections motivate the two extensions below.

由此形成两个设计重点：传输规划纳入预测误差，编码精度匹配任务质量需求。RobustMPC [3] 提供考虑不确定性的规划原则，DynamicKV [4] 提供任务相关缓存分配的证据，支撑下文的两个扩展。

## 7. Literature-grounded proposals / 有文献依据的改进提议

> We propose two extensions: robust bandwidth-aware streaming, inspired by RobustMPC [3], and task-aware precision selection, inspired by DynamicKV [4]. The focus is their design rationale and integration with CacheGen. / 我们提出两个扩展：受 RobustMPC [3] 启发的鲁棒传输决策，以及受 DynamicKV [4] 启发的任务感知精度选择。重点说明设计依据及与 CacheGen 的结合方式。

### 7.1 Proposal A: robust bandwidth-aware KV streaming / 方案 A：考虑预测误差的 KV 传输决策

**CacheGen starting point.** CacheGen estimates future throughput from the preceding chunk and selects a representation using the remaining SLO budget. An optimistic estimate can make a seemingly feasible configuration miss its deadline. We focus on decision robustness while initially keeping the original streaming chunk size fixed. [1, §5.3]

**CacheGen 的出发点。** 原系统根据上一块吞吐量预测后续带宽，再结合剩余 SLO 时间选择配置。若预测过于乐观，预计可行的选择仍可能超时。我们的核心改动是决策的鲁棒性，首先保持原来的传输 chunk 大小，以便分离改动的作用。

**Published evidence.** Yin et al.'s SIGCOMM 2015 paper develops model predictive control for video bitrate selection. Its RobustMPC formulation accounts for throughput uncertainty, and its implementation uses recent prediction errors to obtain a conservative bound. The source locators are §§4.2–4.3 for the mechanism and §7.2, Figures 8 and 10, for evaluation. This provides a methodological basis for considering prediction error instead of trusting a point estimate. [3]

**文献证据。** Yin 等人在 SIGCOMM 2015 研究视频码率决策，通过模型预测控制规划后续分块，并在 RobustMPC 中考虑吞吐量不确定性，利用近期预测误差得到保守边界。方法见 §§4.2–4.3，实验见 §7.2、Figures 8 和 10。这为将预测误差纳入传输决策提供了方法依据。 [3]

![RobustMPC Figure 8: normalized video QoE under throughput traces](assets/robustmpc_fig8.png)

*Source: [3], Figure 8, PDF p.10 / printed p.334. Normalized video QoE under FCC, HSDPA, and synthetic traces. / FCC、HSDPA 与合成轨迹下的归一化视频 QoE。*

**Transfer to CacheGen.** We propose a short-horizon controller over the upcoming chunks. Its state includes recent throughput and prediction errors, the remaining SLO budget, and profiled GPU costs. Its actions select an existing KV encoding level or text recomputation. For each candidate sequence, it estimates completion time under a conservative bandwidth bound, including decoding, recomputation, and their dependencies. It selects a feasible low-loss sequence, executes only the first action, and replans after the next observation. A terminal estimate reserves time for the remaining cache beyond the planning window.

**迁移设计。** 方案对后续分块进行短窗口规划。状态包括近期吞吐量与预测误差、剩余 SLO 时间，以及预先测量的 GPU 成本；动作是在已有 KV 编码等级与文本重算之间选择。对候选动作序列，在保守带宽下估计完成时间，同时纳入解码、重算及其依赖；选出预计可行且损失较小的序列，只执行第一步，再利用新观测重新规划。还需估计规划窗口之外剩余缓存的完成成本，为完整上下文的加载预留时间。

```text
After a chunk completes:
  Update throughput estimates and recent prediction errors.
  Build a conservative throughput bound from the observed error history.
  Enumerate a small set of KV-level/text choices over a short horizon.
  Estimate end-to-end completion time, including GPU costs and dependencies.
  Choose a low-loss plan predicted to fit the remaining deadline.
  Execute its first action, observe the next chunk, and replan.
  If no plan is feasible, record the conflict and apply a declared fallback.
```

**Adaptation objective.** Video playback has a buffer, rebuffering costs, and bitrate-switching preferences. Context loading has a first-token deadline and GPU work, and generation normally waits for the needed context state. The KV controller therefore combines a TTFT deadline with profiled GPU costs and calibrated quality estimates across chunks. [3; our analysis]

**迁移目标。** 视频有播放缓冲、卡顿与码率切换代价；上下文加载则有首 token 时限和 GPU 计算成本，生成通常要等待所需状态就绪。因此，KV 控制器将 TTFT 时限、GPU 成本与跨 chunk 标定的质量估计结合起来。


### 7.2 Proposal B: task-aware precision selection for CacheGen / 方案 B：面向不同任务的 CacheGen 精度选择

**CacheGen starting point.** CacheGen already offers several pre-encoded versions and adapts delivery to network conditions. Our extension adds a task-dependent quality budget to this network-aware selection.

**CacheGen 的出发点。** 原系统已有多个预编码版本，并按网络情况调整传输。我们的扩展为网络感知选择加入任务相关的质量预算。

**Published evidence.** DynamicKV, published in Findings of EMNLP 2025, reports different layer-wise attention and token-retention patterns across task categories. It uses adaptive token-retention budgets. Section 3 and Figure 2 provide the task-difference evidence, while §4 describes budget allocation. DynamicKV allocates token-retention budgets; our extension applies task-aware allocation to CacheGen's encoding precision. [4]

**文献证据。** DynamicKV 发表于 Findings of EMNLP 2025，观察到不同任务的逐层注意力与 token 保留模式不同，并据此调整 token 保留预算。任务差异的证据见 §3 和 Figure 2，预算方法见 §4。DynamicKV 分配 token 保留预算；我们的扩展将任务感知分配用于 CacheGen 的编码精度。 [4]

![DynamicKV Figure 2: task-dependent token-retention patterns](assets/dynamickv_fig2.png)

*Source: [4], Figure 2, PDF p.3 / printed p.8044. Layer-wise token-retention rates across tasks. / 不同任务的逐层 token 保留率。*

**Transfer to CacheGen.** The proposed design associates task-quality requirements with CacheGen's existing encoding levels. Application metadata or a lightweight task classifier identifies the request type. A task profile then defines acceptable versions, and the streaming controller selects among them using current throughput, remaining time, and GPU costs. Reusing pre-encoded versions keeps the online operation a version-selection decision.

**迁移设计。** 方案将任务质量需求与 CacheGen 已有编码等级关联。应用元数据或轻量分类器识别请求类型，任务配置确定可接受的版本，再由传输控制器根据当前吞吐量、剩余时间和 GPU 成本选择。复用预编码版本，使在线操作保持为版本选择。

**Design value.** Task-aware selection makes the quality criterion reflect what the request needs to preserve. QA, summarization, and code completion can use different quality profiles while sharing CacheGen's codec and delivery infrastructure. The precision choice therefore connects the user's task to the network decision.

**设计价值。** 任务感知选择使质量标准反映当前请求需要保留的信息。问答、摘要与代码补全可采用不同质量配置，同时共享 CacheGen 的编码器和传输机制。精度选择由此连接用户任务与网络决策。

### 7.3 Combined interpretation / 两个方向的共同定位

Proposal B defines task-dependent acceptable configurations. Proposal A plans their delivery under uncertain network conditions. Together they form a controller that connects task quality with network conditions. The combined design first identifies task-appropriate versions, then plans their delivery using network and GPU state.

方案 B 筛选任务可接受的配置，方案 A 在不确定网络下规划如何传输。二者构成连接任务质量与网络条件的控制器，先确定任务适用的版本，再根据网络与 GPU 状态规划传输。

## 8. Conclusion / 结论

CacheGen demonstrates that remote KV reuse is a networking problem as well as a computation problem. Its codec exploits properties of KV tensors, and its streamer adapts representation choices to time and bandwidth constraints. Its main advantage is faster loading of reusable long contexts, with lower bandwidth demand and similar task quality. Our proposals extend the analysis toward prediction-error-aware delivery and task-specific quality budgets. Together, the extensions connect robust network decisions with calibrated task-quality budgets.

CacheGen 说明，远程 KV 复用同时涉及计算与网络。其编码器利用 KV 张量的统计特性，自适应传输则根据时间和带宽选择表示。其核心优势是以更少传输量、更低加载延迟复用长上下文，同时保持相近任务质量。我们的提议进一步关注考虑预测误差的传输决策与任务相关的质量预算，将鲁棒网络决策与标定后的任务质量预算结合起来。

**Q1. Why not always recompute from text? / 为什么不总是传文本重算？**  
Long-context prefill can be expensive, especially when GPU resources are busy. The better route depends on effective throughput, GPU speed, and context size. / 长上下文 prefill 可能昂贵，GPU 忙时尤甚；选择取决于吞吐量、GPU 速度和上下文长度。

**Q2. Is CacheGen lossless? / CacheGen 是否无损？**  
Arithmetic coding is lossless, but quantization introduces loss. The paper evaluates the resulting quality trade-off. / 算术编码无损，量化有损，论文评估的是整体质量权衡。

**Q3. Does it accelerate every generated token? / 每个输出 token 都会更快吗？**  
Its main target is loading context before the first token. TTFT measures query arrival to the first output token. / TTFT 衡量请求到达至首 token 输出的时间。

**Q4. Does compression solve GPU memory capacity? / 压缩是否解决了运行显存问题？**  
The transmitted bitstream is compact, but the LLM consumes a reconstructed KV tensor. Runtime memory reduction is a separate concern, although complementary methods can help. / 传输码流变小，但模型仍使用恢复后的张量；运行显存是另一问题，可与其他方法结合。
